# 架构总览

本目录是理解和评审 pi-agent-recall 的主入口。策略、配置及执行链路应在这里形成完整说明，不要求读者从 dated spec 中拼出总体架构。

**当前结论：已有 Profile 参数化的固定注意力规则、执行内核和公开的 `/pi` adapter；完整的可定义策略核心、生产 AnchorProvider 与双消费者迁移尚未实现。**

## 1. 定位与要解决的问题

本库管理“何时重新提供注意力机会”，不是记忆库或任务调度器：

- 已有下一次模型请求时，尽量在该请求中重新提供短锚点，不额外启动推理。
- 没有下一请求时，只有明确停后、无 continuation、锚点和证据有效且预算允许，才可能建议 wake。
- 无有效机会、能力或证据时保持沉默；投递成功不等于模型采用。

core 不依赖 Pi，但独立 core 不能读取内容、监听真实会话或完成投递。可用的整套机制需要宿主组合层；首个目标宿主 Pi 已有公开的 `/pi` adapter，经真实 Pi 1.4.0 零费用 PTY 场景矩阵验证。

| 文档 | 在本目录内负责回答的问题 |

## 3. 状态标记

- **已实现**：当前源码与测试支持的能力。
- **已确认方向、未实现**：用户已确认的完整确定性策略闭环，不等于具体接口已批准。
- **待评审提案**：规则表达、参考策略、接口迁移等具体设计选择。
- **未验证**：当前测试不能证明的宿主或模型性质。

| 能力 | 状态 |
|---|---|
| 一套固定动作规则：已有请求优先 reanchor，停后才可能有界 wake | 已实现；不是命名策略接口 |
| Profile 精确匹配、保守默认、用户覆盖/撤回 | 已实现；不等于策略或参数标定 |
| 生命周期、预算、冷却、去重、预留、prepare/commit、shadow | 已实现 |
| fake clock/sink、候选级确定性 replay、包消费 | 已实现 |
| 独立策略定义、生效参数解析、观察到提案的生成和策略归因 | 已确认方向、未实现 |
| 单一生效策略内的有序规则、两个参考策略、新 Observation 接口 | 待评审提案，未实现 |
| Pi recall adapter | 已实现并经 `/pi` 公开；模型 Tool、Skill 未实现 |
| 真实模型净收益、跨宿主投递契约 | 未验证 |

阶段零完成只对应其限定契约，不能作为完整策略核心完成的证据。真实 Pi V2 测试已加载 recall 测试 adapter，但受控 fixture 通过不等于生产接入、完整生命周期覆盖或模型收益。

当前已经可以通过 SDK 预览/替换参数、关闭/模拟/授权干预、评估外部候选、复核和记回执、查询状态以及离线回放。各操作的实际接口、前提和限制见[当前可执行的策略操作](policy-and-configuration.md#11-当前可执行的策略操作)，不能将这些操作误写成独立策略的创建或切换。

## 4. 模块关系与所有权

| 模块或角色 | 职责 | 不得承担 |
|---|---|---|
| 业务消费者 / AnchorProvider | 提供获准的当前锚点、版本、正文及业务相关证据 | 复制 core 的动作选择和频控状态机 |
| 宿主组合层 | 采集当前事实、管理 session 唯一 owner、重新读取快照并投递 | 猜测业务语义、谎报宿主能力 |
| 策略定义与参数解析 | 定义注意力行为并得到可追溯的生效参数；当前只实现 Profile 部分 | I/O、自动标定、开启未授权动作 |
| 提案生成 | 由标准化观察与锚点元数据产生有界候选；未实现 | 保存正文、替消费者决定业务真相 |
| 执行内核 | 对候选实施统一门槛、预留、复核和记账 | 调用宿主、承诺 exactly-once 或 adopted |
| testing | 经同一公开接口 fake 与 replay | 用模拟提交冒充真实模型效果 |

一个 session 的投递 owner 由宿主组合根明确指定，core 不自动发现或仲裁 owner。策略和消费者都不因此获得独立投递权。

## 5. 当前结构与目标结构

当前结构：

```text
消费者构造候选 + 当前锚点元数据 + 宿主事实
                         ↓
精确 Profile / override → 固定动作选择 → 执行内核
                                           ↓
                              宿主复读快照与同步投递
```

缺口是候选之前的策略定义与生成链路，而不是现有执行内核完全不存在。

目标方向，尚未实现：

```text
配置选择策略 + 可选环境 Profile + 显式覆盖
                         ↓
                  生效策略与参数
                         ↓
外部标准化观察 + 获准锚点元数据 → 策略提案生成
                                       ↓
                              共用同一个执行内核
                                       ↓
                            宿主复核与实际投递
```

core 中不出现正文。消费者在投递前提供当前正文，组合根计算可信大小，只将元数据交给 core 复核。

## 6. 不能被配置绕过的原则

- 生命周期 fence、旧回调失效、唯一 owner 的外部责任。
- 有下一请求时不因 reanchor 被关闭或不支持而升级为 wake。
- wake 需要当前事实证明 settled、无下一请求、无 continuation。
- 版本、期限、大小、证据、预算、冷却、去重和容量必须满足。
- prepare 成功才获得单次许可并计尝试；失败或 unknown 不退款、不自动重试。
- off/shadow/emit 切换不清真实账本，shadow 结果不补发。
- prepare 与同步 sink 之间不得 await；若宿主不能满足，必须重新评审边界。

可配置数值不等于可以禁用检查。参数、权限和运行事实的区别见[策略与配置](policy-and-configuration.md)。

## 7. 仍需书面评审的具体选择

| 提案 | 评审要点 |
|---|---|
| 一个生效策略包含有序、有限的纯数据规则 | 是否足以覆盖目标注意力行为，是否避免过早建设 DSL |
| 观察输入取代外部策略候选 | 消费者提供事实与元数据，core 承担通用注意力提案生成 |
| 策略 defaults + 环境 Profile + 用户覆盖 | 逐字段来源、授权边界、未知环境默认 off |
| 显式策略身份与版本 | 规则变化、Profile 匹配、旧票据失效如何一致 |
| 迁移未发布实验接口 | 不保留能绕过新策略的旧候选执行入口 |

这些选择在架构中留有明确位置，但仍不是当前实现或已批准接口。具体变更规格与验收矩阵见[本轮 spec](../spec/2026-10-25-deterministic-policy-core-design.md)。

## 8. 核心完成与文档完成标准

核心须能从显式策略、环境配置和观察输入走到确定性提案、统一门槛、预留及 fake 投递回执，且保留全部既有安全断言；只新增配置类型或策略名字不算完成。

架构文档须让读者不打开 spec 也能回答：

1. 现在实际支持什么策略，哪些只是开关组合或未实现提案？
2. 策略与配置如何组合，哪些字段可覆盖，哪些门槛不可绕过？
3. 同一观察在不同策略下为何得到不同结果，执行安全如何保持一致？
4. 配置或策略变化会失效什么、保留什么？
5. 哪些能力已实现、哪些待评审、哪些依赖未来宿主验证？

spec 记录某次变更的精确契约、取舍和验收；实施计划记录施工顺序。它们不是总体架构的替代入口。
